# The schema and its migrations

> Part of the `adms-verify` skill, moved here word for word on 2026-10-09 (ADR-445) so the
> skill's own page stays short. **Read this page before you touch `packages/db/prisma/schema/` or a migration, or write a database test for a new table.** Today's counts are
> `agent_store/CHAIN.md`'s, never this page's.

**The schema** (ADR-267, 268), after a change to `packages/db/prisma/schema/`: in `packages/db`, `./node_modules/.bin/prisma validate` (→ `The schemas at prisma/schema are valid`), then `./node_modules/.bin/prisma migrate dev --create-only --name <what>` to generate a migration, reviewed, then `pnpm installer` to apply it. Call the CLI through `./node_modules/.bin/prisma`: `pnpm exec` re-runs the install first. Never edit a generated or applied migration (ADR-113). Two things seen (ADR-281): `migrate dev --create-only` **applies any earlier migration still pending to `adms` itself** before it makes the new one (as `adms_owner`, like the installer; so write a stub's SQL, and try it with its tests on a throw-away copy, before generating the next migration: ADR-311 (9)); and when the generated migration carries a warning it asks to confirm and needs a terminal: `(sleep 6; printf 'y\n'; sleep 8) | script -q /dev/null ./node_modules/.bin/prisma migrate dev --create-only --name <what>`. **A migration that writes a row** (a backfill) states its actor and writes inside one `DO` block: Prisma runs a migration's statements one by one, so `set_config(…, true)` in its own statement is gone by the next (seen on a throw-away copy, ADR-336). **The hook refuses a second write into a stub**: one never applied to `adms` is removed and made again with `--create-only`. **A guard's `--create-only` stub must come out empty** (`-- This is an empty migration.`): if it carries a line nobody asked for, Prisma is reading a `dbgenerated` default back differently from how the schema writes it (KD-70: `CURRENT_TIMESTAMP` comes back as `now()`; `transaction_timestamp()` comes back as written). Fix the schema, never write around the hook. **A deferred check** (a container's primary box, ADR-321) is asked at commit; a database test asks it with `SET CONSTRAINTS ALL IMMEDIATE`, and the example world does once it is built. **A field event's tests** (ADR-324): `field-events.test.ts`, one test per scenario ID of `spec/acceptance/04-field-capture.md`; a test writes one with `fieldEventLike` or `backOfficeEventLike` and `eventInsertOf`, since no column of where it came from has a default; a new column joins `captured` in `grants.test.ts` and AC-04-25's exact column list. **What each kind records** (ADR-325): `field-event-kinds.test.ts`, one test per scenario ID; a debris type is written with `debrisTypePicked(world, entryId[, form])` (the entry with its form and document type), a split collection with its estimate, a measurement with `measured_as`; a new kind-specific column also joins `packages/domain`'s `fieldEventDetails` and `packages/contracts`' `fieldEventDetailsSchema`, and the test "every detail on every kind" then tries it on all five kinds. **Scale receipts and photographs** (ADR-326): `scale-receipts-and-photos.test.ts`, one or more tests per scenario ID; a test writes a receipt with `scaleReceiptLike` and a photograph's record with `photoLike(world, owner)`, both through `phoneInsertOf` (the id a phone would make); a photograph's fingerprints and keys can't be updated, so a test that needs others writes another; a new owner of a photograph widens `photo_owner_check` and joins `correctable.photo` in `grants.test.ts` and AC-04-76's column list; a new latitude or longitude column joins the exact list in `sites.test.ts`. **ROEs and forms** (ADR-327): `roes-and-forms.test.ts`, one or more tests per scenario ID; a test writes an ROE with `roeLike` and a survey, an incident or a drop-off log from `formLike` or `backOfficeFormLike` plus its own columns, through `phoneInsertOf`; `answers` is always stated, and answers come with `form_definition_id`, `form_id` and `form_document_type` together; a new form table joins `formShared`'s users in `grants.test.ts`. **Intake and quarantine** (ADR-338): `quarantined-records.test.ts`, by scenario ID of `spec/acceptance/05-sync.md`; a test writes a quarantined record through `phoneInsertOf('quarantined_record', …)` with the field event or the ROE that holds its number, and what the phone sent can't be updated afterwards, so a test that needs other values writes another; the stories `sync` and `p1-any-order` drive `apps/api`'s `Intake`, and a record a phone never makes is a phone's record copied under a new id and handed to `story.intake.receive`. **The derived records** (ADR-340): `derived-records.test.ts`, by scenario ID of `spec/acceptance/06-reconciliation.md`; a test writes them as the worker (`db.as('adms_worker')`, `db.actor(world.worker, 'SYSTEM')`) with that file's `completedLoadLike`, `collectionRowLike`, `flagLike` and `runLike`; a rule that holds only among live rows is an exclusion `WHERE dissolved_at IS NULL` (refused as `refusedBy.exclusion`), never a partial unique index, and `./node_modules/.bin/prisma migrate diff --from-migrations prisma/migrations --to-schema prisma/schema --exit-code` (→ `No difference detected.`) shows Prisma won't drop it; a cross-project refusal is tried with a record nothing else names yet, or another key answers first and the test proves nothing (seen: one of fifty loosenings slipped through that way). **A priced line** (ADR-358): `transactions.test.ts`, by scenario ID of `spec/acceptance/07-pricing-ledger-audit.md`; a test writes one as the worker with `transactionLike(world, more)`, and the tickets the example world doesn't hold with `new PricedTickets(tested)` (`test/support/priced-tickets.ts`); `transaction` has its own guards, so a new column means its viewer view and column grant written again by hand in the guard migration, `viewerColumns.transaction` in `grants.test.ts` and AC-07-89's column list; the two-column foreign keys to the completed load and to the completed haul-out are implied by the row's three-column key and the check, so loosening one alone is not caught, by construction. **People's marks** (ADR-363): `marks.test.ts`, by scenario ID of `spec/acceptance/08-review-and-corrections.md` and `09-invoice-deliver-closeout.md`; a test writes them as the API's login for the person (`actingAs`) with that file's `qcLike`, `lockLike`, `acceptanceLike` and `voidLike`; every mark states its `project_id`, and a mark on a field event `field_event_kind: 'UNIT_RATE'`; a second lock or void in force is `refusedBy.exclusion`; what a mark is on, who made it and when can't be updated, nor a lock once unlocked or a void once lifted, so a test that needs other values writes another. **A reviewer's services** (ADR-364, 365) have no test project of their own: their rules are `packages/domain/test/review.test.ts` and they are driven whole by the stories `p1-reviewed` (corrections and renumbering) and `p1-voided` (void, unvoid, accept; `pnpm scenarios p1-voided`, under ten seconds once built; both need the map servers); **a loosening of a service or of the worker's reading of a mark is tried on the story** (change the source, `./node_modules/.bin/tsc --build`, run the story, put the source back from a copy kept in the scratchpad, build again); the audit log's `occurred_at` is the database's clock, so a story tells "after" by the audit record's id. **Loosened guards may be tried on part of the tests** (ADR-363): the files that hold the table's guards (its own, `catalog`, `grants`, `transactions`, `transaction-delete`, `viewers`, `guard-table`, `audit`, `no-delete`; never `configuration`, which a bare copy fails by itself), since a loosening caught by part is caught by the whole; say that it was a part. **The tests ask the copy for the newest migration by name**, so a guard still in the scratchpad can't be tried as loose SQL unless the copy's `_prisma_migrations` is told the stub is applied (its file's SHA-256 as the checksum): do that on a throw-away copy only, then write the stub once and prove it again with `migrate deploy`. **A loop of loosened guards took about four minutes a pair here on 2026-10-05** (fifty took 110 minutes, with 873 tests a run; it was 75 seconds a copy at 500 tests)**; two at a time** (twenty took 25 minutes, ADR-323): run it in the background with no ten-minute limit, and give the script absolute paths. **A setup version** (ADR-453): `setup-manifests.test.ts`; a test writes one as the API's login for a phone (`db.actor(deviceKeyActorId, 'DEVICE', { deviceId: world.device })`), numbered 1 then 2, each with other content, since the numbering trigger refuses a number out of turn and the same content again; none can be updated, so a test that needs other values writes the next version. **A guard may be tried before its stub is made** inside one rolled-back transaction on `adms` as the server's administrator (`BEGIN`, the table's migration, the guard's SQL, `SELECT * FROM guard_gaps()`, a few writes, `ROLLBACK`): DDL is transactional and nothing is kept. **A loosening of a guard's function** is the function's text from `pg_get_functiondef` with one string swapped: make the swap where a missing string fails (Python's `assert s.count(old) == 1`), never with a shell's `${var/…}`, which reads `(` and `+` as a pattern and leaves the text as it was (seen 2026-10-09: three loosenings counted as slipped that had changed nothing).
