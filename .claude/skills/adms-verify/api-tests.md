## 1.3b The API's tests (ADR-385)

`apps/api/test`, by scenario ID of `spec/acceptance/10-api-and-sync.md`. `settings.test.ts`,
`error-filter.test.ts` and `boundary.test.ts` need no stack (the last two run the real process in
memory, with one more controller of the test's own, started through `test/support/process.ts`;
two of the first start the built `apps/api/dist/main.js`). `request-id.test.ts` runs the process
in memory too but opens `adms` as the API's own login, and undoes its write by failing out of it.
**After a change to an endpoint in `packages/contracts`, `pnpm openapi`** (it writes
`apps/api/openapi.json`; `boundary.test.ts` fails on a stale file, and on a route the contracts
don't list). A test's own endpoint is made with `endpoint()` from schemas the contracts export:
`apps/api` has no Zod of its own (ADR-387).
`door.test.ts` asks the API's own container through Caddy over HTTPS and reads its log with
`docker compose logs`: it **needs `pnpm local:up` after `pnpm installer`**, and fails saying so.
**The container runs what was built when it started: after any change to `apps/api`, `pnpm
local:up` again** (it builds, makes the container afresh and prints `https://api.adms.localhost/health
→ 200 {"status":"ok"}`). Until the installer has run, `local:up` says `The API waits for pnpm
installer` and starts the six. By hand:

```bash
curl --cacert infra/local/.generated/caddy-root.crt https://api.adms.localhost/health   # → {"status":"ok"}
curl -sI http://api.adms.localhost/health                                               # → 308 to https
```

`passwords.test.ts` (ADR-402…405) needs no stack: the hash, the release's breached list, the
reset code, the mail settings and what the two reset endpoints refuse before anything is read.
`password-set.test.ts` writes: it opens `adms` as the API's login and **runs each test in one
piece of work that is undone** (`test/support/database.ts`, `undone`; the services are handed a
database whose `$write` and `$read` run inside it; a Prisma piece of work ends after five
seconds, so a test stays short), hands the process its own database, mail and clock
(`ProcessParts`), and sends one message through the stack's mail catcher, read back at
`https://mail.adms.localhost/api/v1/…` and deleted. **A loosening of the password rules, the
hash, the reset code or `Passwords` is tried on these files and on
`packages/domain/test/passwords.test.ts`** (change the source, run the file, put it back). The
secrets scan reads `apps/api/openapi.json` and every test: a made-up login URL is put together
in `support/process.ts`, never written whole.

`session-tokens.test.ts` (ADR-408) needs no stack: the access token, the refresh token, the
CSRF value, the cookies, and what an endpoint that asks for a session refuses on sight; **it
holds the list of endpoints nobody need be signed in for**, so a new `ANYBODY` endpoint is
added there on purpose. `sessions.test.ts` (ADR-408…411) writes, as `password-set.test.ts`
does: its `Served` starts the process on the test's own piece of work with a `TestClock` and
keeps a browser's side (cookies and the CSRF value, by hand); `test/support/sign-in.ts` puts
sign-in's services together for a test that calls one directly. **Every endpoint a test defines
states its `access`.** An audit record's id is a BigInt: never `JSON.stringify` one whole.
**A loosening of sessions, wrong tries, the cookies, admission or the hasher is tried on those
two files, `passwords.test.ts`, `password-set.test.ts`, `boundary.test.ts` and
`packages/domain/test/sign-in-tries.test.ts`**: fifty-seven took about ten minutes as a script
that swaps one string, runs the files and puts the source back (format first, or the strings
don't match; a loosening that isn't found in the source proves nothing: count it as not
tried). **To copy `adms` for a guard's loosening, stop the API's container first** (`docker
stop open-adms-local-api-1`: it holds a connection), and `pnpm local:up` again afterwards.

`enrolment.test.ts` (ADR-439) is a phone enrolled under the master passcode: a real enrolment, the key, wrong tries, the wait, the lock and its opening, the log. **The installation's own master passcode is unknown to a test: each test adds a version of its own inside its undone piece of work** (`passcodeSet`) and enrols under that with a software key. An address's fifth wrong try is answered 429, so a test that makes more moves `served.from`; the lock is reached with `installationPolicy({ SIGN_IN_TRIES_BEFORE_LOCK: '7' })`. A key another phone holds is the database's refusal: a test's last request. **Never send a real or a wrong enrolment to the container** (`door.test.ts` sends one its schema refuses): a phone can't be deleted, and a wrong try counts against the installation's own passcode. A loosening of `Enrolment` or its controller is tried on it (it imports the source; thirteen took under two minutes as a script that swaps one string, **reading vitest's stderr with its stdout**); one of the guard on `packages/db`'s `master-passcode-actor.test.ts`, `catalog.test.ts` and `grants.test.ts` on a copy. **A new table that names a user** joins `packages/db/test/support/master-passcode-actor.ts`, with its check in its guard. **A new `ANYBODY` endpoint** joins `session-tokens.test.ts`'s list.

`phone-proofs.test.ts` (ADR-440) is a phone's proof of itself: a challenge asked for and answered, the token, a recorded answer sent again, every proof that isn't one, a phone out of service and one whose key is revoked, the log. **A test's phone is `test/support/phones.ts`'s**: `enrolledPhone(served, tx, name)` enrols by the API's own request with a software key under a passcode version of the test's own, `answered` and `proven` ask for a challenge and sign it, and `served.ask(…, { bearer })` sends a token; **no test writes a phone by hand** (the database refuses a key that isn't shaped as one). **It holds the exact list of the endpoints open to a proven phone** (`access: 'PROVEN_PHONE'`): a new one is added there on purpose. `phone-proof.test.ts` needs nothing: the key, the challenge, the token, and two answers to one challenge at once (a database of the test's own making whose write matches no row). `door.test.ts` asks the container for a challenge and sends it a proof for a phone nobody enrolled: neither writes anything. A loosening of `PhoneProofs`, `PhoneTokens` or `Admission`'s phone access is tried on those two files (fourteen took about two minutes); **the early refusal of a revoked key and the rule asked before the write are each doubled by the write's own condition**, so loosening one alone changes nothing: loosen both. One of the guard on `packages/db`'s `device-key-actor.test.ts`, `catalog.test.ts`, `devices.test.ts` and `master-passcode-actor.test.ts`, each on its own copy (twelve took about seven minutes, one at a time). **A database test writes a device key with `deviceKeyLike(name)`** (`test/support/device-keys.ts`). **A story enrols a phone with `story.enrolled(name, at?)`** and proves one with `story.proofs`: never `tx.device.create`.

`phone-sign-ins.test.ts` (ADR-443, 444) is a monitor's sign-in on a phone: who may sign in, the device's session (a row naming the phone, twelve hours, sent as `x-adms-monitor-session` beside the phone's token), what ends it, wrong tries, the per-person count, the log, **and the assignment the phone takes** (its project and board written through the endpoints as Dana; the day moved with `served.clock.at`, the phone proved again after it). The rule itself is `packages/domain/test/assignments.test.ts`'s (a loosening of `takenAtSignIn` is tried there; one of `PhoneAssignments` on this file, which imports the source). **A story creates a monitor with `story.monitor(name, onPhone)` and takes their assignment with `taken(story, monitor, phone)`** (`stories/board.ts`): never `tx.user.create` for a monitor; a monitor's sign-in writes a security event and a session, which a story's exact audit list holds. **The installation must be at head** (`pnpm installer` after a migration made elsewhere), or every signed-in API test answers 500. **A test's monitor is made the real way** (`created`: `POST /phones/current/monitors` under the test's passcode) and signed in with `signedIn`; a call open to `MONITOR_ON_PHONE` is `served.ask(…, { bearer, monitorSession })`. **It holds the exact list of the endpoints open to `MONITOR_ON_PHONE`**: a new one is added there on purpose. A phone answers only a challenge made after its last, so **a test that sets the clock earlier sets it before the phone is enrolled**, and one that moves it past fifteen minutes proves the phone again. A loosening of `PhoneSignIns`, its controller, `Admission`'s phone accesses, `WrongTries` or `Sessions` is tried on it, `sessions.test.ts` and `phone-proofs.test.ts` (eighteen took about forty minutes; an archived monitor's check and a phone's session at the back office are each doubled by construction). One of the session's guard on `packages/db`'s `sign-in.test.ts` and `catalog.test.ts`, each on its own copy. **On a Linux host** (a cloud session) the API's and the worker's containers run as uid 1000: the two service env files after `pnpm installer`, and the Caddy root `local:up` copies, must be readable by that user, or the API or the worker doesn't start (`ADMS_MAP_CA_FILE is malformed`).

`phone-lists.test.ts` (ADR-450) is the lists a phone reads (`GET /phones/current/lists`): what they carry for the assignment the phone takes, a refresh after the board or the setup changed, and who may ask. **It holds the exact list of the endpoints open to `MONITOR_ON_PHONE` by name** (`phone-sign-ins.test.ts` holds it with roles and permission: a new one joins both). Its world is `leeOnP1`: P1 priced through the endpoints (`p1Priced`), a phone, Lee Morgan created and signed in, and helpers to write an assignment, add a debris type to the load form and a field tag. **A list the service gains joins the exact expectation, the "never" strings and the contracts' shape test** (`packages/contracts/test/api-answers.test.ts`, which reads every field name of `phoneListsSchema`: `apps/api` has no Zod of its own). AC-07-91's pattern reads field names, never words: the value `UNIT_RATE` and the field `contractors` are right to send. Loosenings of `PhoneLists` are tried on this file. **Since ADR-451** it also makes what no request makes yet, each as its service or its table does: a certification through `Certifications.certify` and a phone's block through `NumberAllocator.topUp` (both on `within`, the fourth thing `world` hands a test), an ROE and a survey by `tx` (as `review-records.test.ts` does); `leeOnP1(served, tx, more)` hands the project's other settings on (`ticketNumberSource: 'CONTROL'` for control ranges). **Its "never" checks read the answer's text and its field names**: a pattern over field names must not catch a list's own name (`fieldTags` holds `tag`). A loosening of `PhoneLists` is tried on this file alone. **Since ADR-453 a read writes one thing, a setup version:** the first read of a project in a test makes version 1 (one audit record of `setup_manifest`, the device key's actor on that phone) and a read after a change to what phones are shown makes the next; a read after a new certification, ROE or board change makes none. A test's own `tx` writes after a read carry the last actor a service stated (the device key's), which the database allows the API. A loosening of `SetupVersions` or of the trim in `PhoneLists.held` is tried on this file.

`phone-login-list.test.ts` (ADR-454) is the login list and the master passcode's check (`POST /phones/current/login-list`). **A check is tried as a phone would try it** (`opens(typed, check)`: Node's own Argon2 twice, nothing of the API's), so the test proves what a phone can do with what it is sent. Its world is its own `leeOnP1` (Lee created, assigned to P1 for Monday and signed in; `created`, `signedIn`, `assigned(personId, workDate[, ids])`); `holding(answer)` is what a phone says it holds after taking an answer in. A policy value of its own goes through `worldOn`'s third argument (`installationPolicy({ LOGIN_LIST_ENTRIES_PER_CALL: '1' })`). `offline-checks.test.ts` needs no database. **A loosening of `phone-login-list.ts`, `offline-checks.ts` or of where a seed is kept** (`phone-monitors.ts`, `passwords.ts`, `phone-sign-ins.ts`) is tried on these two files. **A new endpoint is named in the contracts' `endpoints` list as well as defined** (seen 2026-10-09: the boundary's routes and both exact lists failed until it was).

`phone-address-lookups.test.ts` (ADR-455) is an address looked up for a phone's GPS (`POST /phones/current/address-lookups`). **Its first test asks the local stack's own address server** (Delaware's roads: `39.15650000, -75.52330000` is "25 The Green"), handed to the process as `ProcessParts.addresses` through `worldOn`'s fourth argument (`asking(stacks)`); the others hand it a `Told`, an address server of the test's own that keeps what it was asked, so a test can say **nothing reached the address server**. A lookup writes nothing, so its world is a phone and Lee signed in, no project. **Its "never" checks read the log's whole text** for the point and the address. `packages/domain/test/addresses.test.ts` is the reading of an answer and needs nothing. **A loosening of `address-server.ts`, `address-lookups.ts`, its controller or the API's map settings** is tried on this file, the domain's and `settings.test.ts` (they import the source); one of the endpoint's definition needs `./node_modules/.bin/tsc --build` first. **A new required setting of the API** joins `settings.test.ts`'s `good`, `passwords.test.ts`'s hand-built settings and `support/process.ts`'s `madeUpSettings` (seen 2026-10-10: one test failed until it did), and an installation made before it needs `pnpm installer --yes` once (`pnpm ready` shows the `✗`). **Typed into a file, `\u2028` in a regex may be written as the raw character**, which a regex literal can't hold: check with `grep -n 'u2028'`.

`phone-unplanned-assignments.test.ts` (ADR-457) is an unplanned assignment reported by the phone it was made on (`POST /phones/current/unplanned-assignments`, `PROVEN_PHONE`: `served.ask(…, { bearer })`, nobody signed in). Its world is `tariqAtTheLandfill`: P1 priced, the Landfill, a unit rate and a hauling pay item, the tower's phone and Tariq created on it; `setUp(more)` is the report a phone sends, with an id of its own each time. **A security event a phone reported is told from one the server saw by its offset** (`deviceUtcOffsetMinutes` not null): a test's own enrolment and monitor already leave two `MASTER_PASSCODE_USE` on the phone. **Moving `served.clock.at` on more than five minutes ends Dana's access token** (sign her in again) **and more than fifteen the phone's** (`proven` again). **A refusal the service answers with a 200 writes nothing, so a test may go on after it**; two of one report at one moment are the database's refusal and can't be told inside a test's one piece of work. A loosening of `unplanned-assignments.ts` or its controller is tried on this file (it imports the source); one of `AssignmentRules.unplannedDay`, `.mayHoldUnplanned` or `.reportedAgain` on `packages/domain/test/assignments.test.ts`; one of the guard on `packages/db/test/assignments.test.ts` and `sign-in.test.ts`, each on a throw-away copy. **`assignments.test.ts` receives its unplanned assignment through this endpoint**: the database refuses one written any other way. **Since ADR-458 a report states `occasion`** (`setUp` says `SETUP`; a site move is `setUp({ siteId, madeAt })`, a switch `setUp({ personId, occasion: 'MONITOR_SWITCH', madeAt })`), and the file has `signedIn(served, token, monitor)` and `tookAt(answer)` for the assignment a sign-in took; a second monitor is created on the phone as Tariq is. A loosening of which assignment a sign-in takes is tried on `packages/domain/test/assignments.test.ts` (the rule) and on this file (`phone-assignments.ts`'s read); **one of the request's own list of values doesn't build**, which is the compiler's refusal.

`phone-passcode-sessions.test.ts` (ADR-462) is a session opened on a phone under the master passcode (`POST /phones/current/passcode-sessions`, `PROVEN_PHONE`, the passcode in the body). Its world is `theTowersPhone(served, tx, at?)`: P1 priced, a phone, Tariq and Lee created on it with no assignment, and `setUpFor(monitor)`, an unplanned assignment reported for Monday so that the phone takes one (a temporary session's end is its project's day). `opened(served, bearer, personId, kind)` is one that must open; `sessions(tx, phone)` every session on the phone. **A day's end is tried by starting the world in the evening** (`mondayEvening`) and proving the phone again after `served.clock.at` moves; `served.clock.later` takes minutes, and more than fifteen ends the phone's token. `GET /phones/current/monitor` now answers `masterPasscodeSession` (null on a monitor's own sign-in): an exact expectation of it names the field. **A reported switch ending the earlier session** is `phone-unplanned-assignments.test.ts`'s last test. A loosening of `passcode-sessions.ts`, its controller or `onPhone`'s read of the mark is tried on this file; one of the switch's rule on `phone-unplanned-assignments.test.ts`; one of `PasscodeSessionRules` or `ProjectClock.dayEnds` on `packages/domain/test/passcode-sessions.test.ts`; one of the guard on `packages/db/test/sign-in.test.ts` and `catalog.test.ts` on a throw-away copy (**stop the API's and the worker's containers first, and restore the function between loosenings** with the migration's own text: six took about two minutes on one copy).

`phone-setup-choices.test.ts` (ADR-463) is what a phone being set up under the master passcode picks from (`POST /phones/current/setup-choices`, `PROVEN_PHONE`, the passcode in the body). Its world is `theStagingArea`: P1 priced with two sites and three pay items, the county's parks as a second open project (`another(name)` makes one more), a phone, Tariq and Lee created on it. **Every test's world already has one monitor, Kim Nguyen** (`who.kim`, `who.kimsId`), created before any phone's: an exact list of monitors begins with her (`kim(who)`). `shown(served, bearer, more)` is a read that must be answered, with the answer's whole text for the "never" strings. **The bound on monitors is tried on the service itself**, built on the test's own `within` with `monitorsAtMost: 1` (no test makes a thousand monitors). A site, a pay item or a project is archived or closed by `tx`. A loosening of `setup-choices.ts`, its controller or `SetupVersions.sitesShownIn` / `.payItemsShownIn` is tried on this file **and `phone-lists.test.ts`** (both reads share those two; twenty-five took about four minutes).

`phone-passcode-uses.test.ts` (ADR-464) is a use of the master passcode a phone logged with no connection (`POST /phones/current/passcode-uses`, `PROVEN_PHONE`, no passcode sent). Its world is its own `theTowersPhone`: P1 priced, a phone, Tariq and Sam created on it, and Sam's Monday planned by Dana on that phone; `logged(use, personId, more)` is the report a phone sends, with an id of its own each time. **A use's first security event carries the phone's own id, so ids say nothing of the order: its `events` reads a request's events by kind.** `SecurityEvent.createdAt` is the database's clock, never `served.clock`. A use the contract gains joins the domain's `loggedPasscodeUses`, the refusals in its first test and the story `under-the-passcode`. A loosening of `PasscodeUses`, its controller or the contract's refinement is tried on it; one of `PasscodeLogRules` on `packages/domain/test/passcode-uses.test.ts`. **The guard on what a phone reported** (`security_event_a_phone_reported`) is `packages/db/test/sign-in.test.ts`'s: a database test that writes a security event with an offset states the master passcode's actor for that phone first; its condition on the source can't be seen to slip, since ADR-438's guard already lets that actor state no source but a phone.

`packages/contracts/test/sync-records.test.ts` (ADR-466) is the records a phone syncs and needs nothing: one of each kind from the example world, what is taken as sent (a gap, a fix that couldn't be one), what is refused (an unknown field, a value past its bound), and **a pattern over every field name the schemas take** (a new field that reads like a conclusion, money or the phone fails it on purpose; `typedCapacityCy` is the one capacity). **`apps/api/src/sync/sent.ts` is typed from those schemas**: a field added to one reaches `Intake`, `RecordWrite`, the harness's `device.ts` and `review-records.test.ts`'s `disposal` through the compiler. A record read by the schema and saved by `Intake` is `review-records.test.ts`'s last test. A loosening of a record's schema is tried on the contracts' file (it imports the source). **Since ADR-469 a certification is its seventh kind** (`certification` and `crew` in `src/sync-examples.ts`: the example world's self-loader `730416` and bucket truck crew `730417`); the pattern over field names holds it too, so what a certification replaces is `replaces.replacedId`, never a `certificationId`. **A certification read by the schema and made by `Certifications.received`** is `apps/api/test/certifications.test.ts`'s last test (a phone by `enrolledPhone`, an assignment by `tx`; the refusals first, since `certify` asks before it writes; a photograph naming the certification through `Intake`): a loosening of `received`, of `Intake.photo`'s owner or of the domain's `NotSaved` is tried on it, the contracts' file and the domain's `intake.test.ts` together, with `tsc --build` (one whose types no longer fit doesn't build: try it in another form). ESLint refuses a class instance spread into an object (`{ ...NotSaved.x() }`): name its fields.

`packages/contracts/test/sync.test.ts` (ADR-467) is one sync whole and its answer and needs nothing: what is sent and in what order, the four limits, each record read on its own by `recordRead`, what a record that isn't one is told, and every answer's shape. **The example records both files send are `src/sync-examples.ts`** (one of each kind, Monday on P1, and the two example reports; moved beside the source by ADR-470, since the suite sends them): a new kind of record joins `records` there. The two reports a sync carries are `phone-reports.ts`'s, the ones their endpoints read: a change to either is a change to `apps/api/openapi.json` (`pnpm openapi`). **A loosening of the sync contract is tried on `sync.test.ts` and the domain's `intake.test.ts`, with `tsc --build`** (the contracts read the domain's `dist/`).

`packages/contracts/test/sync-client.test.ts` (ADR-470) is the suite any client of the sync contract must pass (`syncClientSuite`, `src/sync-client-suite.ts`) and the rule a client reads an answer by (`syncAnswerRead`, `src/sync-client.ts`); it needs nothing. Its `phone(fault?)` is a client in memory that keeps the contract, or breaks it in one named way: **a check the suite gains comes with a fault that only it catches, added to `faults` and to the exact map of which checks catch which.** `packages/scenarios/test/sync-client.test.ts` runs the same suite on the harness's phone (`SimulatedDevice.hold`, `sends`, `answered`, `holds`, `shownNotSaved`) and tries `SyncStandIn`, with no database. **A loosening of the suite, `sync-client.ts`, the phone's `sends` / `answered` or the stand-in is tried on those two files and `harness.test.ts`, with `tsc --build`** (twenty took about two minutes). **A limit's check must hold more than a sync's worth after whatever is made to wait** (seen 2026-10-11: one record waiting on its unplanned assignment left exactly 200, and a phone with no limit passed). `"saved"` under no id can't be seen to slip in `syncAnswerRead`: `recordAnswerSchema` takes no such answer. **A story's own intake answers each record under that record's id** (`heldId(sent)`): the phone takes an answer under any other id for no answer, and the story stops ("what came back is no answer to the sync it sent"). **A harness test's made-up list ids are UUIDs** (`listId(name)` in `harness.test.ts`): the phone's records go through `syncedRecordSchema` at a sync, and a pick that isn't one is answered `NOT_SAVED`. **The phone's sync is a whole sync at a time:** one that gets no answer leaves every record it carried on the phone, and the next sends them all again.

`sync.test.ts` (ADR-472) is a phone's sync, whole (`POST /phones/current/syncs`, `PROVEN_PHONE`: `served.ask(…, { bearer })`, nobody signed in). Its world is `kimOnP1`: P1 priced, a phone enrolled and proven, Kim's Monday written by `tx` (loads at both ends, certifying), and `event`, `disposal` and `sync` to make what a phone sends from the contracts' `syncExamples` with ids of the phone's own. **`synced` reads the answer by the client's own rule (`syncAnswerRead`)**; a sync that carries what is no record is read with `syncAnsweredSchema` instead (the client's type takes only records). `syncsOf`, `ledgerOf`, `jobsOf` and `heldOf` read what a sync wrote. **A record that names an id the test's world lacks (a debris type, a site) is the database's refusal, which ends a test's one piece of work:** the example records are sent with `formDebrisTypeId: null` and `siteId: null`, and **the one test of a database's refusal builds `Sync` itself on `within` with each `$write` behind a savepoint** (`each` in that test), which is what a piece of work of its own comes to in the process. **Two collections on one cert number at the same times are neighbours:** a job then names both tickets. A held record's audit row holds `[kept out of the audit]` for `payload`. **`phone-proofs.test.ts` holds `syncPhone` in its exact list.** A loosening of `sync.ts`, its controller, `ledger.ts`, the ledger row or the job in `Intake`, or the row in `Certifications.certify` is tried on this file (it imports the source; thirty took about three minutes); **a retry is answered by the ledger's look and by `Intake`'s own (for a certification, by the look by its id), so loosening one alone changes nothing: loosen both**; one of `recordNames` on `packages/contracts/test/sync.test.ts`, one of `NotSaved.heldForReview` on `packages/domain/test/intake.test.ts`, each with `tsc --build`. A loosening that rewrites an id's first character proves nothing: a UUIDv7 begins with `0`. **Since ADR-473 a sync says what it holds** (`p.sync()` states the passcode version the phone was enrolled under and no lists, so nothing more is brought and nothing more written; a test that wants a check sends `masterPasscodeVersion: null`, one that wants a setup version `listsProjectId`), and the test that builds `Sync` itself hands it a `PhoneLoginList`. **A check a phone was sent is tried with `opens` (`test/support/offline-check.ts`)**, shared with `phone-login-list.test.ts`. An audit record's `changedFields` on an INSERT is every column: compare it only on an UPDATE. A loosening of what a sync brings is tried on this file (`sync.ts`, `phone-login-list.ts`'s `passcodeBrought`, the controller: eight took under a minute); one of the contract's `holds`, the two brought schemas or `syncAnswerRead`'s setup-version rule on `packages/contracts/test/sync.test.ts` and `sync-client.test.ts`.

`limits.test.ts` (ADR-416): rate limits. **A test's requests come from `served.from`**
(`support/served.ts`): four wrong tries at one login from one address and the fifth is answered
429 before the login is touched, so a test that makes more moves `served.from`; a test that
needs other numbers hands `worldOn` (or `Served.on`) a policy from `installationPolicy({ … })`.
A new policy value (the newest: `PHONE_TOKEN_MINUTES`, ADR-440) is added to `policy.env`, the three whole maps in `packages/domain/test/`
(they have no Node types to read the file with), `project-settings.test.ts`'s list of names and
`packages/scenarios/test/policy.test.ts`.
